# 16 - 对标产品 pentest-platform 的结果验收闭环

> 只读分析：`harness/pa_kernel/pentest/`（hunt_flag / vulnerability_submission / finding_envelope / hunt_vulnerability / journal）、`server/apps/ctf/`、`server/apps/engine/`、`server/apps/findings/`。
> 判定口径：每条结论必须有 file:line；指不出行号的只当推断，不当结论。

## 0. 结论先行

它打满分的根本原因不是"模型更强"，而是**"得分"这件事根本不由模型宣布**：flag 提交后由外部平台 `correct=true` 裁决，服务端按 `accepted 行数 ≥ flag_count` 判满贯，finding 报告面完全不参与计分。我们要修的"用不相关证据标记目标达成"，在它那里是一段**先决条件链**：没有 accepted 就没有 outcome 节点，没有 outcome 节点就过不了五格校验，过不了就不许 `goal_met`（`server/apps/ctf/services.py:583-656`、`server/apps/engine/planner/verdict.py:249-281`）。这是"构造上做不到"，不是"提示词要求别做"。

## 1. 提交即记账：四态各自的落点

`hunt_flag` 是宿主本地工具，`call()` 里 `await asyncio.to_thread(self.flag_submit, flag)` 拿到服务端回包，紧接着在**同一个调用栈**里 `_settle()` 按 status 分派（`harness/pa_kernel/pentest/hunt_flag.py:181-194`）：

| 状态 | 动作 | file:line |
|---|---|---|
| accepted | `append_note(kind='outcome', title='[FLAG] <flag>')` → 自动落 L1/L2 图、计 notable、唤醒 mission_result | `hunt_flag.py:209-229` |
| rejected / duplicate | `append_note(kind='intel')`，不 notable、不唤醒 | `hunt_flag.py:230-245` |
| transport_error / captured | 零 note，台账已入账，`retry_pending` 幂等兜底 | `hunt_flag.py:246-253` |
| ok=False（链路错） | 零 note，error 透传 | `hunt_flag.py:200-208` |

"落 outcome 由工具保证，不再依赖 LLM 自觉双写"（`hunt_flag.py:28-37`）的机制就一句：**提交与记账是同一个函数的两个连续语句，模型没有第二次调用机会去"补记"**。之前在 tsec-6 出的"静默 flag"是模型提了 flag 却没写 outcome；现在 outcome 的写入条件被写死在 `if status == "accepted"` 分支里，模型连参数都没有。同时参数面收窄到只有一个 `flag` 字符串（`hunt_flag.py:82-96`，`extra=forbid`），题号由服务端从 run→战役→锚资产解析（`hunt_flag.py:86-88`、`server/apps/ctf/services.py:415,509-516`），"地址四级 LLM 抄写链"整条被删除。

服务端侧同样是一次调用完成三件事：`capture`（幂等入账）→ `submit`（外呼裁决）→ 组装回包（`server/apps/ctf/services.py:496-532`）。

## 2. 重复提交怎么防

rejected/duplicate 变成**负结果情报节点**，链路是：intel note → L1 `entry`（`server/apps/hunts/services.py:99-101`）→ L2 `GraphNode.kind='intel'`（`server/apps/engine/hunt_sync.py:24-27,143-147`）。兄弟 agent 通过 brief/图增量看到这条负结果，但**不唤醒 planner**（`hunt_sync.py:128-131` 只对 `outcome` 与 `[finding-candidate]` 计 notable；`hunt_projection.py:39-43`）。这是关键取舍：错误值得被记住，不值得触发一次规划。

更硬的一层在台账：`(project, unique_code, flag_sha256)` 唯一约束（`server/apps/ctf/models.py:44-49`），`_claim_for_attempt` 对终态直接返回 None 不发请求、对 180s 租约内的 pending 去重（`server/apps/ctf/services.py:182-203`），409 归 duplicate（`:158-160`）。

**与"16 次诱饵提交"是否同一问题**：同根，但不等价。他们缺一不可的三件是"唯一键 + 终态不可变 + 负结果上图"。我们那 16 次是三者全缺——没有以 flag 内容哈希做主键，rejected 被当作"无结论"丢弃，于是兄弟看不到"这个值是诱饵"，每条新意图都重试一次。诱饵问题的本质不是模型笨，是**否证没有落账**。

## 3. 漏洞验收：结构化字段门，不是语义门

写前（PA 侧）有硬门，entry 不落盘、当场报错：`body_md` 四节（摘要/技术细节/影响/修复建议）对 `supported` 必须全非空 + 必须有 `proposedSeverity` 或 `cvssVector`（`harness/pa_kernel/pentest/finding_envelope.py:312-360`）；`vulnerabilityClass` 与 `reproduction` 非空（`:363-394`）；http 步骤的 `request` 首行必须是请求行，curl 形直接拒并给转写对照（`:188-207`）；`cvssVector/cweIds/cveIds` 正则（`vulnerability_submission.py:821-854`）；`supported` 的最小必填集走同一份 map 判定（`:897-955`、`:777-804`）。

服务端再校验：schema、CVSS base score 必须与 vector 重算一致（`server/apps/findings/services.py:219-230`）、severity/confidence rationale 非空（`:212-217`）、`potential` 必须在 limitations 解释不确定性（`:243-251`）。

**有没有"证据必须与结论匹配"的校验？有，但只是"引用可解析"，不是"内容能推出结论"**：confirmed/highly_likely 需要至少一条带 `artifact_id` 的证据、步骤 `evidence_refs` 要在本 finding 内解析——两项都是 `soft: True`，只入 `intake_warnings` 不改判（`services.py:232-241`、`server/apps/findings/intake.py:22-49`）。真正硬的证据链只有一条：`evidenceRefs` 对账 workspace evidence 账本，命中才写 `artifact_sha256`（`vulnerability_submission.py:311-346,400-403`）——这是**内容寻址**，保证"引用的文件确实存在且没被改"，不保证"这个文件证明了 SSRF"。

结论：验收是规则匹配 + 结构化字段，判的是"形状齐全"，语义相关性交给下游人看。它能满分，正因为计分不靠这一层。

## 4. 三态区分：没有统一枚举，是三级独立载体

| 态 | 载体/字段 | file:line |
|---|---|---|
| 已采集 | `CtfFlagSubmission.status = 'captured'`（`capture` 幂等 get_or_create） | `server/apps/ctf/models.py:13-19`、`services.py:127-141` |
| 来源已核 | `technical_evidence.evidence[].artifact_sha256`（对账 sweep 账本，命中才有值，未命中降级 `locator.fragment`） | `vulnerability_submission.py:400-403`、`:311-346` |
| 结论已核 | `vulnerability.status ∈ hypothesis/investigating/supported` → `disposition`（potential/highly_likely/confirmed） | `vulnerability_submission.py:66-72`、`hunt_vulnerability.py:517` |
| 第三方已裁 | 台账 `accepted/rejected/duplicate/transport_error`，来源是平台回包而非模型 | `ctf/services.py:144-179` |

值得注意：`confidence.level → validation_status` 只映射到 `unverified` / `partially_verified`（`vulnerability_submission.py:645-656`），**全库没有 "verified" 这一档**。他们诚实地承认"模型自称 confirmed ≠ 被验证"，验证档位留给外部裁决（flag 台账）和人工 triage。我们若想照搬，别急着造三态枚举——三级各自有判据、且互不覆盖，才是它的形态。

## 5. 工具层与模型层的边界

**代码强制（模型绕不过）**：参数面只有 flag（`hunt_flag.py:82-96`）；题号服务端解析（`ctf/services.py:415`）；四态→note kind 的分派（`hunt_flag.py:198-259`）；台账唯一键与终态（`ctf/models.py:44-49`、`services.py:191-203`）；满贯判定的 accepted 计数 + 战役作用域 outcome 证据 + 五格校验（`ctf/services.py:642-656`、`verdict.py:249-281`）；四节/评级/curl 形状门（`finding_envelope.py:188-207,312-394`）；CVSS 重算（`findings/services.py:219-230`）；提交幂等三层（`vulnerability_submission.py:168-180,1059-1142`）；`stable_submission_id = sha256(run_id)[:16]` 使崩溃重发落同一条记录。

**只靠提示词/软警**：四节里的正文是否胡说（只判非空）；评级标尺（`_supported_rationale_warning` 只是 warning，`hunt_vulnerability.py:472-490`）；证据与结论的相关性（soft）；零 finding 时的 `no_findings_reason` 自由文本（`vulnerability_submission.py:1011-1016`）。

比例大约是 **9 项硬 / 4 项软**，且分布有明确规律：**"结论/记账/身份"100% 代码强制，"叙述/论证质量"0% 强制**。这条分界线是它最值得抄的东西——它没试图用代码判"这个漏洞分析得好不好"，只判"这个结论有没有被谁裁决过"。

## 6. 可直接照搬的 3 条

1. **提交与记账合并成一次工具调用**（`hunt_flag.py:181-235`）。Pojun 的 `submit_flag` 是外部 MCP 工具，回包只进工具结果，模型不写就丢。改法：在 `agent/tools.go` 的 submit 包装里，拿到回包后立刻写库——`(task_id, challenge_code, flag_sha256)` 唯一键 + 状态机（captured/accepted/rejected/duplicate/transport_error），并在 accepted 分支里直接落一条 `KindFact`（带 receipt）。模型没有任何"补记"入口，静默提交在结构上消失。
2. **负结果也必须上图**（`hunt_flag.py:230-245` + `hunt_sync.py:128-131`）。Pojun 已有否证 fact 机制，但缺 flag 级的专用抑制键。把 rejected/duplicate 写成带 `(challenge_code, flag_sha256)` 的 fact，frontier 取意图前查这张负结果表——16 次诱饵提交会被压成 1 次。
3. **收尾判据锚在外部裁决上，不锚在模型自述上**（`ctf/services.py:642-656`）。Pojun 已有 `prove_goal` + `Unverified` 标记（`agent/tools.go:1644-1700`、`server/dto.go:225`），差的是"证据必须带外部回执"这一条：证据节点若由外部平台回包派生（含 receipt/sha256），才允许判 met；纯模型 fact 只能标 unverified。改动量小，收益是把"被证明"和"被声称"彻底分开。

## 7. 不能照搬的 2 条

1. **五格校验本身搬不过去**（`verdict.py:249-281`）。它挡的是空列表/不存在/跨项目/非 active/kind 非事实类——**挡不住"语义不相关"**。在 pentest-platform 里它够用，是因为 evidence 集合由 `campaign_outcome_evidence` 单一构造，而 outcome 节点全库只有 `hunt_flag` 的 accepted 分支会写（`ctf/services.py:565-580`、`hunt_flag.py:209-219`）。Pojun 的 fact 由 worker 自由写入，把 kind 门抄过来只是多一道形式检查，`prove_goal` 照样能被一个不相关的 fact 满足。要抄的不是这个函数，是"结果节点只有一个写入者"这个前提。
2. **战役作用域的 evidence 口径搬不过去**（`ctf/services.py:565-580`）。它依赖"一题一锚资产 + `Campaign.flag_count`"的战役模型（`:583-632` 的守护链全部建立在 flag_count 上）。Pojun 没有 flag_count，任务边界是 `task_scope`，硬套会把"要不要收工"绑到一个不存在的计数上，最终要么恒不收、要么造一个假计数。Pojun 该保留自己的四判据（`server/auto_finish.go:94-114`），只把其中"目标达成"这一支换成外部回执锚。

一句话总结：**它没有一个环节相信模型的自述；它把"谁说了算"从模型手里拿走了三次——题号归服务端、判决归外部平台、关门归 tick。**
