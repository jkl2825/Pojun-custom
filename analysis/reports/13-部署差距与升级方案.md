## 2. Schema 迁移：只有 2 列，全幂等，不需要停机

`git diff f716742 HEAD -- db/schema.sql` 净变化 7 行，全是注释 + 两条 DDL：

```sql
ALTER TABLE exploration_nodes ADD COLUMN IF NOT EXISTS first_run_at TIMESTAMPTZ;
ALTER TABLE exploration_nodes ADD COLUMN IF NOT EXISTS escalation_level INT NOT NULL DEFAULT 0;
```

- 这两列**本来就是我们自己加的**（意图阶梯，判定逻辑在 `server/escalation.go` + `db/escalation.go`），不是上游改动。上游 0.4.48–0.4.54 没有碰 `exploration_nodes`，冲突面为零。
- 幂等性：`IF NOT EXISTS`；`escalation_level` 带 `NOT NULL DEFAULT 0`，PG11+ 走 fast default 只改元数据，不重写表，加锁时间与表大小无关（线上 `exploration_nodes` 当前 0 行）。
- 应用方式：`db/db.go:21` 是 `//go:embed schema.sql`，启动时整份 `Exec`（`db/db.go:280` 注释明确「schema.sql is Exec'd on every startup，所以必须保持幂等」）。所以**迁移是随重启自动完成，没有独立迁移步骤，也不需要停库**——停的只有应用进程那 2–3 秒。
- 线上实测已生效：`information_schema.columns` 里 `first_run_at`、`escalation_level`、`blocked_reason`、`delete_reason` 全在。
- 无删列、无改类型、无新增 `CHECK` 约束。这一条直接决定回滚可行性（见 §5）。

## 3. 配置项差异：没有新键

schema 里 `settings` 段在本次 diff 中零变化；线上 `settings` 55 行，与 0.4.47 一致。新增的自动收尾判据、凭据闸门阈值等都在代码常量或既有键的取值域内，不需要人工补配置。唯一需要人工确认的是升级页的「覆盖式升级保护」——本地定制版禁用了官方二进制安装，`server/update.go` 已改（+51 行），页面点「一键更新」不会把定制版覆盖成上游版。

## 4. 镜像与工具链：必须重建 app 层，但不必重建底座

`docker/`、`.github/`、`ops/` 共 +830 行。关键结论：**不能只 `docker cp` 换二进制**。原因是前端 `server/webui/dist` 是静态导出后 `embed` 进 Go 二进制的，二进制与镜像层必须同源；而 `Dockerfile.local` 的设计正是如此——`FROM pojun-local/pojun:0.4.47-sapper-collab-20261105`（已验证的工具/浏览器/CA 底座，37.6GB）再加 `COPY dist/amd64/pojun`。所以代价是「Go 编译 + npm 前端导出 + 一次薄层提交」，**不是重装 37GB 工具链**。

实测代价：HEAD 提交 06:56:16 → 镜像创建 07:04:31，**约 8 分钟**。`docker/install-tools.sh`（170 行）只影响底座重建，本次未触发；它带三轮重试是为了跨 GitHub 抖动，真重建底座是 40 分钟以上的事，属于另一档风险。

## 5. 回滚路径：够用，且 schema 已先一步兼容

现有回滚资产：镜像 `pojun-local/pojun:before-upstream-v054-20261105`（升级前，2 小时前）、`:0.4.47-sapper-collab-20261105`（底座）、容器内 6 份 `.bak-*` 二进制（`bak-0.4.46`/`046b`/`browser-mcp`/`resentinel`/`idlefix`/`aging`/`ladder`/`reconcile`）。

**关键判断：回到 0.4.47 不会因 schema 报错。** 迁移纯增量，旧代码 `SELECT *` 到结构体时多余列被忽略；`escalation_level` 有默认值，旧代码 INSERT 不指定该列也不违反 `NOT NULL`。风险只在「回滚后新写入的数据语义」——本次库里 `tasks`/`explorations`/`exploration_nodes`/`assets`/`findings` **全是 0 行**，等于空库，所以连语义漂移都不存在，现在回滚是零成本窗口。

## 7. 结论

**状态：升级已完成并稳定运行，不需要再升一次。判定为「已完成、可接受、需补验收」。**

数据支撑：18 条提交里 schema 只净增 2 列且都 `IF NOT EXISTS`，线上两列已存在、服务已在新版本上跑满 46 分钟无 schema 错误——即最高风险项（迁移）实际风险为零；反过来说，继续留在 0.4.47 反而要吃 0.4.49 拦截误伤和 0.4.51 角色边界这两个会直接污染数据的缺陷。

真正的风险不在升级动作，而在运维纪律：一是 **tag 漂移**（`:0.4.54-custom-20261105` 这种名字不可复现，重建同名 tag 会悄悄换掉回滚点，应改用 `SOURCE_REVISION` 短 sha 做 tag）；二是 **镜像堆积**，20 个镜像、可回收 8.1GB，`docker system df` 显示 build cache 22.8GB，C 盘剩 157G 但 `/app/data` 在涨，需要 `ops/disk-guard.sh` 定时跑。

## 8. 升级步骤（命令级，供下次复用）

```bash
cd /path/Pojun
# 1. 冻结点：记录当前运行镜像 digest，作为唯一回滚坐标
docker inspect pojun-pojun-1 --format '{{.Image}}' | tee /tmp/rollback.digest
docker tag pojun-local/pojun:0.4.54-custom-20261105 pojun-local/pojun:rollback-$(date +%Y%m%d%H%M%S)

# 2. 数据备份（先库后文件，库是唯一不可重建的部分）
docker exec pojun-postgres-1 pg_dump -U pojun -Fc pojun > backup/pojun-$(date +%Y%m%d-%H%M).dump
tar czf backup/data-$(date +%Y%m%d-%H%M).tgz data/ --exclude=data/traffic

# 3. 编译（前端静态导出 + Go 交叉编译，产物必须在 dist/amd64/）
./build.sh --target linux/amd64

# 4. 构建 app 层镜像（底座复用，约 1 分钟；编译本身约 5–8 分钟）
docker build -f Dockerfile.local \
  --build-arg BASE=pojun-local/pojun:0.4.47-sapper-collab-20261105 \
  --build-arg SOURCE_REVISION=$(git rev-parse --short HEAD) \
  -t pojun-local/pojun:0.4.54-$(git rev-parse --short HEAD) .

# 5. 换容器（--force-recreate 才会拾取新镜像；restart 不会）
POJUN_IMAGE=pojun-local/pojun:0.4.54-$(git rev-parse --short HEAD) \
  docker compose up -d --force-recreate pojun

# 6. 验证点（四条全过才算成功）
sleep 20
docker logs --tail 50 pojun-pojun-1 | grep -E "backend listening|schema|migrat|error"
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8887/api/health
docker exec pojun-postgres-1 psql -U pojun -d pojun -c \
  "select column_name from information_schema.columns where table_name='exploration_nodes' and column_name in ('first_run_at','escalation_level');"
docker exec pojun-pojun-1 sh -c 'strings /app/pojun | grep -m1 "mod.*chu0119/pojun"'
```

## 9. 回滚步骤

```bash
# A. 首选：镜像回滚（不碰数据，10 秒级）
docker compose down pojun
docker tag pojun-local/pojun:rollback-20261105xxxx pojun-local/pojun:0.4.47-rollback
POJUN_IMAGE=pojun-local/pojun:0.4.47-rollback docker compose up -d pojun

# B. 若要连数据一起回（仅在确认新版本写坏了数据时）
docker compose stop pojun
docker exec -i pojun-postgres-1 psql -U pojun -d postgres -c \
  "drop database pojun with (force);" -c "create database pojun owner pojun;"
docker exec -i pojun-postgres-1 pg_restore -U pojun -d pojun --clean --if-exists < backup/pojun-xxxx.dump
docker compose start pojun

# C. 验回滚
docker logs --tail 20 pojun-pojun-1 | grep "backend listening"
```

注意 A 与 B 的区别：schema 只增列，**A 是安全的默认动作**；B 会丢掉升级后新产生的全部数据，只在数据被写坏时才用。另：**不要**用 `docker cp` 把 `.bak-*` 拷回 `/app/pojun` 再重启——镜像层里的前端产物与二进制版本会错配，页面白屏；`.bak-*` 只作二进制取证留档。
