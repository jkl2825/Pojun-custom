## 一、结论

**没有被改坏。** 补丁触及的 59 个文件全部存活，其中 53 个与补丁提交**字节一致**（`git diff aac06e6 HEAD -- <file>` 为空），其余 6 个的净改动全部来自上游新增或合并期的构建策略重写，无一条删除本地语义。两处调度机制（idle-stop 双条件、Frontier 老化排序）判据、阈值、提示语均与昨晚验证过的版本完全一致。零冲突残留，全仓可编译，`go vet` 三包零告警，测试除环境性缺项外全绿。

## 二、方法

1. 用 `git log --graph` 与 `git log -1 --format=%P 7ad0184` 确认拓扑：`7ad0184` 的两个父提交正是 `aac06e6`（本地）与 `234dd89`（上游），合并基 `f716742`。因此 `git diff aac06e6 HEAD` 的净差集就是「上游 v0.4.54 + 两次合并提交」对本地补丁的全部影响面，不需要逐条读冲突片段。
2. 用 `git diff --name-only f716742 234dd89` 取上游改了哪 21 个文件，与补丁的 59 个文件求交集——交集只有 4 个（`.dockerignore`、`agent/tools.go`、`hosttools/hosttools.go`、`report/findings.go`），其余 55 个文件上游根本没动，**结构上不可能**被合并破坏，只需确认文件仍在。
3. 对交集 4 个文件逐个读净 diff，判断是「删除本地语义」还是「上游追加」。
4. 用「同包重复定义必然编译失败」这一硬约束替代人工比对重名函数：`go build ./...` 通过即证伪重复定义，再辅以机制层的人工核对（同一件事有没有两条实现）。
5. 机制验证采用「读代码 + 定向跑测试」双证据，不只依赖代码文本。

## 四、冲突与重复

- 合并残留标记 `<<<<<<<` / `>>>>>>>` / `=======`：全仓 **0 处**，无 `.orig`/`.rej`。
- 同包重复函数定义：`go build ./...` 通过（同包重复定义必然编译失败），可判定不存在。
- 机制层重复只有一处**语义重叠但不冲突**：上游 `SetIntentBlockedReason`（强制置 blocked，仅 LLM 配额路径）与本地 `ParkIntent`（带阶梯等级）。二者调用点互不交叉；重开逻辑 `ReopenIntentsByBlockedReason` 只按 `IntentBlockedLLMQuota` 这一 reason 匹配，不会批量撤销阶梯停放；`ReopenBlockedIntents` 仅由人工端点 `server.go:1355` 触发。

## 五、并存机制的先后与叠加

1. **任务级自动收尾（上游 v0.4.26 `recordAndEvaluateAutoFinish`）vs 意图级阶梯停放（本地）**：作用域不同，不会双重执行。但存在一处**间接耦合**：停放把意图置 blocked 后，`HasActiveIntent()`（只数 open/running）会转 false，理论上可让 auto-finish 的「frontier 抽干」判据提前成立。该耦合在合并前（`aac06e6`）就已存在，非本次合并引入。
2. **`addFinding` 三重证据闸**：本地 v0.4.5 证据门槛 → 上游 v0.4.52 机械凭据 → 本地 v0.4.29 逐字回验，串行叠加（`tools.go:1725/1731/1738`）。这是本次合并唯一新增的叠加，方向是更严而非更松。
3. 调用链顺序已核对：`plannerLoop` 的 escalation ticker 与 planning 心跳独立（`engine.go:1182` 注释「持续的 worker 完成事件不能推迟阶梯检查」），未被上游的 settle 通知路径吞掉。

完整调用链（实际读到的代码，不是推测）：

```
plannerLoop (engine.go:1178)
  ├─ case <-escalation:            // time.NewTicker(time.Minute)  engine.go:1003
  │    └─ checkEscalation(t)       // server/escalation.go:86
  │         ├─ RunningIntentsWithClock()  → LastYieldAt(intent)
  │         ├─ decideEscalation(elapsed, sinceYield, level)   纯函数
  │         └─ L4: ParkIntent() → KillWork()
  └─ case <-t.notify / heartbeat.C:
       ├─ runRound("edge"|"heartbeat") → recordAndEvaluateAutoFinish()   // 上游 v0.4.26
       └─ maybePendingSettle() → requestSettle() → settle              // 上游
```

两条链共用同一个 goroutine 的不同 select 分支，互不重入；`recordAndEvaluateAutoFinish` 先跑完再进下一次 select，不会与 `checkEscalation` 并发改同一意图状态，唯一的交互面是它读 `HasActiveIntent()` 时看到的快照。
